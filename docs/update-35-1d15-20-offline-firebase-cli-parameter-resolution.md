## What "real CLI" means, and what it does not

The probe **does not execute the `firebase` command**. Instead it
imports only local Node modules from installed Firebase CLI:
`firebase-tools/lib/deploy/functions/build` and
`firebase-tools/lib/deploy/functions/params`.

It reads the D15.17 source block, uses the **real Firebase Functions
SDK** to declare the string parameter and callable, then
**explicitly translates** the SDK's `serviceAccountEmail` parameter
expression into the CLI Build's `serviceAccount` field.
It sends this **two-endpoint synthetic build** directly into
`resolveBackend` (non-interactive, emulator secret-avoidance flag).
No project object from Google Cloud is queried, and no SDK call
loads the complete production `functions/index.js` module.

Test cases are intended to demonstrate:
1. Runtime versions: Node 22, pinned `firebase-tools@15.28.2` and
   `firebase-functions@6.4.0`.
2. Valid synthetic input resolves exactly the parameter expression
   `{{ params.ODDS_BACKEND_STATUS_SERVICE_ACCOUNT }}` to the
   **invented** `test-status@offline.invalid` account in the
   **single** status endpoint's backend configuration.
3. A second synthetic callable does **not** acquire that account,
   exposing accidental global-scope assignment.
4. Omitting the required parameter in **non-interactive**
   resolution raises a CLI error before producing a backend;
   invalid/unknown CEL references must not silently succeed.
5. No ordinary Node `net`/`tls`/`http`/`https`/DNS/`fetch`
   network calls are observed during probe execution.

Public npm registry access occurs **before** tests begin. Node
method-level network overrides are not a full OS firewall or
guarantee against every native/child-process path. The test's
synthetic project name (`offline-fixture-only`) and identity
have no relationship to actual Firebase accounts; do not reuse
them for deployment.

## Hard limitations

**No production deployment readiness is established by this test.**
Specifically, this probe does **not** validate:
- an actual Firebase CLI deploy discovery cycle, SDK wire manifest
  conversion, parameter value file/prompt handling, change plan,
  API enablement, or IAM `actAs` permissions;
- whether parameter discovery could prompt even when deploying a
  different Function in the same codebase;
- preserving Cloud Run's current ingress, `allUsers` Invoker,
  concurrency, timeout, instances, existing environment values,
  runtime identity and revision routing;
- current installation of `firebase.cmd` on the owner's PC
  (this is an **isolated pinned library version**, not the local CLI);
- the exact deployed source or a safe targeted rollback;
- effective inherited/conditional/deny/policy-boundary IAM,
  two unclassified environment-variable names, cost or billing;
- real callable behavior on Android/desktop or any real provider
  communication.

The prior D15.19 SDK finding also remains important:
`StringParam.value()` in that SDK returns an empty string for a
missing **runtime** env variable. The CLI's noninteractive
missing-param failure does **not** guarantee runtime fail-closed
behavior or validate actual account privilege. This is why a
nonempty expected value and effective IAM must be separately
attested during an authorized release.

**Never run `firebase deploy --dry-run` against production as a
supposedly read-only validation:** Firebase CLI warns that dry-run
may still enable APIs in the targeted project.
